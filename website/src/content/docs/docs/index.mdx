You have an idea for an application and understand what it needs to do. As it grows,
you need a way to keep its rules clear, explain its behaviour, and change it with
confidence.

NeoHaskell brings a language, application framework, and development tools together
around that work. Describe the actions people can take, the facts your application
records, and the information it shows. Work with a coding agent to implement those
decisions, then check the result against your intent.

## Software you can keep understanding

A first version is only the beginning. People ask for new behaviour, rules change,
and an application becomes responsible for work that has already happened. You
need to explain that work as well as add the next feature.

AI makes it easier to produce an implementation. It also makes it important to be
precise about the meaning of a change. “Update this address” could mean a preference
for the next order or a change to an order already in progress. Both can be easy
to code. Choosing the right meaning requires understanding the process.

NeoHaskell connects that understanding to a shared model. The model describes
what people can request, which rules apply, which facts the application records,
and what people need to see. Those concepts have corresponding places in the
implementation, so you and your agent can discuss the same behaviour at different
levels of detail.

*Start with a rule you can explain. Follow it into the model and implementation,
then compare the observable result with what you intended.*

## Why the past matters to the next change

When an application shows a value, it is often showing the result of earlier
actions. A balance comes from money movements. A reservation status comes from
requests, confirmations, and cancellations. Keeping only the current result can
leave you unable to explain how it came about.

NeoHaskell's application framework records accepted changes as events. It uses
that history to reconstruct state and prepare views. A correction can become an
explicit new fact, and a new report can use information already retained. You
choose which facts and context the application needs; the framework cannot recover
a reason that was never recorded.

That is one part of the philosophy. Another is to make a change small enough to
understand: a complete request, decision, recorded outcome, and useful result.
These slices give a coding agent a bounded task and give you something concrete
to verify. Together, a shared model, retained history, and explicit boundaries help
an application remain understandable as it grows.

## Begin with the ideas

The introductory journey gives these ideas room before asking you to install a
tool or read code:

1. **[Why NeoHaskell?](/start/why-neohaskell/)** What changes when implementation
   becomes easier, and why a model of meaning matters.
2. **[History and change](/start/history-and-change/)** How facts explain a current
   value, and how a correction can preserve what happened.
3. **[Growing by slices](/start/growing-by-slices/)** How explicit boundaries help
   people and agents work on one understandable capability at a time.
4. **[Fit and tradeoffs](/start/fit-and-tradeoffs/)** What the approach offers your
   project, where its costs appear, and how to evaluate it.

You can stop there with a useful understanding of NeoHaskell. Continue into the
modeling exercises and working examples when you want to experience the approach
for yourself.

## Learn with a practice project

The worked examples gradually build a small ecommerce application, starting with
one product and a cart. This gives you a familiar setting in which to try each
concept. You can follow the practice project or apply the same ideas to your own
application.

The executable foundations are the public NeoHaskell starter and reference
application. Each lesson distinguishes working code from features you design and
implement as exercises, such as payment and shipping policies.
