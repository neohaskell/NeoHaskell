Your first milestone is a project of your own. You will create it with `neo`, the
NeoHaskell command-line tool, then grow it through the following chapters. The
same directory will hold your code, tests, configuration, and visual model.

We call the practice project `mug-shop`. It is a small application you are about
to build. You can choose another name and use that directory wherever the guide
says `mug-shop`.

## Prepare your tools

Use macOS or Linux; on Windows, work inside WSL2. Install Git and
[Nix for your operating system](https://nixos.org/download/). Nix supplies the
compiler and build dependencies selected by your project. You do not need to
install GHC or Cabal separately.

Check that both commands are available in a new terminal:

```sh
git --version
nix --version
```

Neo uses Nix flakes. If your Nix installation has not enabled them, add this line
to `~/.config/nix/nix.conf`, preserving any existing settings:

```ini
experimental-features = nix-command flakes
```

## Install Neo

Download the executable for your computer from the
[Neo releases](https://github.com/neohaskell/NeoHaskell/releases/latest).

:::note[Release requirement for this draft]

These examples target the upcoming NeoHaskell release that exports all five
`derive…` helpers through `Core`, including `deriveEntity`, together with the
corrected Neo compiler preset. The published 0.10.0 CLI and its framework pin
are not sufficient: correcting the CLI alone does not add the new framework
helpers. Use the matching release once available. You should not need to add
language settings to your source files.

:::

| Computer | Download |
| --- | --- |
| macOS, Apple silicon | `neo-aarch64-apple-darwin` |
| macOS, Intel | `neo-x86_64-apple-darwin` |
| Linux or WSL2, Intel/AMD 64-bit | `neo-x86_64-unknown-linux-gnu` |
| Linux, ARM 64-bit | `neo-aarch64-unknown-linux-gnu` |

For example, on an Apple silicon Mac:

```sh
mkdir -p "$HOME/.local/bin"
curl -fL https://github.com/neohaskell/NeoHaskell/releases/latest/download/neo-aarch64-apple-darwin -o "$HOME/.local/bin/neo"
chmod +x "$HOME/.local/bin/neo"
export PATH="$HOME/.local/bin:$PATH"
neo --version
```

For another platform, replace the final filename in the download URL with the
one from the table. Keep the destination filename `neo`. Add the `export PATH`
line to your shell's startup file (`~/.zshrc` for zsh, or `~/.bashrc` for bash)
to make Neo available in future terminals too. The release includes `SHA256SUMS`
if you want to check the downloaded file's checksum.

The command prints the installed Neo version. `command -v neo` shows which
executable your shell found. When upgrading, check both so an older installation
does not take precedence on your `PATH`.

## Create the application

From the directory where you keep your projects:

```sh
neo new mug-shop
cd mug-shop
neo build
```

Accept the project details or choose your own when Neo prompts. `neo new` creates
an application with a small starter, a test suite, and pinned dependencies.
`neo build` compiles it. The first build can take longer while dependencies are
downloaded or built; later builds reuse that work. Nix may ask whether to trust
the project's declared binary caches.

The starter includes a counter as sample code. In the next chapter you will
replace its application wiring with your first cart feature, inside this same
project. There is no counter exercise to complete first.

## Find the parts you will change

| Location | What you do there |
| --- | --- |
| `src/App.hs` | Connect your services, queries, event store, and web transport. |
| `src/Shop/` | Add the application features you will write in this guide. |
| `tests/` | Describe behaviour and check it repeatedly. |
| `neo.json` | Set project details and declare additional dependencies. |
| `flake.lock` and the `neo-version` in `neo.json` | Keep the resolved dependency versions reproducible. |
| `event-model.json` | Save the visual model when you start using the IDE. |

`src/Shop/` and `event-model.json` arrive in the next steps; they need not exist
in the fresh starter. Neo generates the lower-level build files from your
configuration and source modules. Make project changes through `neo.json` and
rerun `neo build` instead of maintaining generated build files by hand.

Keep the dependency pins that `neo new` supplies. They identify the framework
revision compatible with the starter. Upgrading is a deliberate project change,
with its own build and behaviour checks.

## Learn the daily loop

You will keep using these commands from the project root:

| Command | What it gives you |
| --- | --- |
| `neo build` | A compiler check of the application and its wiring. |
| `neo run` | A running application for trying requests. |
| `neo test` | Your project's repeatable behaviour checks. |
| `neo ide` | A visual workspace for exploring the application's model. |

A successful build is your setup check for now. In the next chapter you will
create a cart, send a request to it, and read back the result. That connects
compilation with behaviour you can actually inspect.

If a command fails, keep its full error and use
[troubleshooting](/reference/troubleshooting/). If you already have an application,
apply the new feature there rather than running `neo new` again.
