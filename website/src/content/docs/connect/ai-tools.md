title: Constrain AI tools

A model can translate an ordinary-language request into a structured proposal: add an item, schedule a task, or update a draft. Your application still decides which object may change, whether the proposed values are valid, and whether the person must confirm the action.

NeoHaskell's agent integration describes tools using command schemas and decodes the returned arguments into a command. This gives structure to the handoff. It does not make model-generated arguments trustworthy or grant the model the user's identity. We will practise with “I want two blue mugs” in the ecommerce example.

Prerequisites: [AI requests](/connect/ai/), [commands](/build/commands-and-events/), and [permissions](/build/access-control/).

## Extend the same mug-shop project

Complete the [integration setup](/connect/#prepare-your-project). Put the
model request helper in `src/Shop/Integrations/CartAssistant.hs`, and define its
proposal command under `src/Shop/Cart/Commands/`. Register that command with the
Cart service with `InternalTransport` before adding the handler in `src/App.hs`.

The command is new application behaviour. Do not expose the existing `AddItem`
as a model tool and assume its positive-quantity check is an ownership policy.
Begin with a proposal that the shopper can inspect before a separately
authorised action changes the cart.

## Begin with a proposal command

Start with a command that records a proposal for review. For the practice cart, keep checkout, payments, and irreversible actions outside its reach. The server should bind trusted cart/user context itself, rather than accepting ownership claims generated by the model.

`Agent.commandTool @YourCommand` obtains the wire name from `NameOf`, a description from `Documented`, and JSON Schema from `ToSchema`. Use the command marker and the established [command conventions](/build/commands-and-events/); provide the schema and documentation instances required by your command's actual derivation path.

The following is a **partial request expression**, not a complete command implementation:

```haskell
Agent.agent
  customerMessage
  [proposalTool]
  modelName
  recordProposalFailure
  |> Integration.outbound
```

`proposalTool` is a `CommandTool`, normally bound once using `Agent.commandTool`. The request's `command` type must support JSON encoding/decoding and a command name. Its error callback returns that same type, so the type needs a deliberate way to represent failure as well as the successful proposal.

The current execution instance lives in `Integration.Agent.Internal`. Although the API description is provider-neutral, this implementation sends requests through OpenRouter using `OPENROUTER_API_KEY`.

## Understand exactly what executes

The current implementation:

1. Rejects an empty tool list through the error callback.
2. Sends a non-streaming request with tool choice required.
3. Reads the first choice's first tool call.
4. Checks that the returned tool name is among the allowed names.
5. Decodes its arguments as the single `Request command` type.
6. Emits that command for the application dispatcher.

It does not run a multi-step planning loop or execute every tool call in a response.

**Multiple tool descriptions do not automatically dispatch to different Haskell command types.** All returned argument shapes must decode into the request's one target type. A sum/envelope design needs an explicit, tested decoder; start with one compatible tool shape.

## Keep authority in the application

The integration dispatcher uses a trusted system context for emitted commands. That bypasses the external access gate; it is not the original user's authenticated request context. Business rules in the command still matter, but you must design the identity and authority boundary explicitly.

For an assistant acting on user requests, a safe first design is to record a proposal bound to trusted request information, show it to the user, and require a normal authorised confirmation command. Treat any model-generated entity ID or permission claim as untrusted input.

Tool-name allowlisting prevents an unlisted name from being accepted. It does not prove that arguments for an allowed name are safe. Likewise, a system prompt is guidance to a model, not an authorisation mechanism.

## Test the proposal boundary

Run `neo build` to check the new proposal command and model request types. Add
fixed tool-call responses to your `tests/` suite and run `neo test`, especially a
response naming another cart. With `neo run` and development credentials, make
one live request and inspect the proposal before confirming it. The ordinary
cart summary should change only through the authorised follow-up action.

## Rehearse a misunderstanding

> **Jess:** “The shopper asked for two mugs. Why does the proposal mention another cart?”
>
> **Agent:** “The model included that cart identifier.”
>
> **Jess:** “Bind the proposal to the authenticated request's cart and reject conflicting identifiers. Show the test.”

Check empty tools, unknown tool names, malformed arguments, no tool call, multiple returned calls, invalid quantities, another customer's identifier, and a harmless-looking prompt that asks the model to ignore its restrictions. Inspect the proposal and the eventual confirmed result separately.

**Exercise:** decide whether an ambiguous product name should create a proposal or ask the shopper to clarify. Write the expected outcome before prompting the model. The acceptance rule should remain stable when you change models.

If you need different provider behaviour or a richer execution loop, continue with [custom integrations](/connect/custom-integrations/).
