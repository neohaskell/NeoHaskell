# Architect runner prompt

The orchestrator passes this file through to every parallel candidate runner during Phase B and fills in the variable inputs around it: the task, the Phase A grounding artifacts, the isolated working directory, and the path to write outputs. The working directory is a git worktree when available, otherwise a per-runner subdirectory under the sketch dir. What matters is independence between candidates.

You are producing one candidate design in architect's parallel exploration. Read the **architect** skill in full first. That's the workflow you're inside. Output a candidate design package: type sketch, function signatures, module map, and prose rationale shaped per [`rationale-template.md`](rationale-template.md).

Apply the following discipline. The orchestrator compares candidates on these axes to pick a base.

- Caller's usage first. Write the usage and two or three realistic Haskell call sites before the types, then derive the type sketch from them. Use internal framework callers or public API consumers according to the actual target. For a service record, show construction, injected dependencies, and use of its operations where relevant. The usage is the spec. The two must agree, so reconcile the sketch to the usage, not the reverse.
- Data structures first. Get the core types right and the code becomes obvious. Trace each dominant access pattern through the proposed structure. If the answer is "we'll add a map / index / cache later," the structure is wrong.
- Interface depth. Compare the capability hidden behind the public surface relative to the size of that surface. Prefer a simple interface that pulls complexity into the callee, even when the implementation becomes less simple. Keep private transport, storage, and wire representations behind their owning boundary. Framework types and intentional interoperability types may belong in the public contract, per **boundary-discipline**.
- Shared state: identify the owning subsystem, invariant and lifecycle. Reuse or extend its operations; separate genuinely independent state. When synchronization is needed, choose the existing NeoHaskell concurrency module whose guarantees preserve the whole operation, per **separate-before-serializing-shared-state** and **foundational-thinking**.
- Make boundaries visible. Use Haskell signatures, comments and explicitly marked pseudocode for incomplete logic; state intent and invariants. Keep incomplete definitions within sketch artifacts or the declared scaffold phase. Explain pure data dependencies and effectful operations where relevant; a type signature alone may not establish evaluation behavior or ordering.
- Encode invariants in types: hard-to-misuse types > runtime checks > prose comments, per the **encode-lessons-in-structure** principle skill.
- Validate at the owning boundaries and trust established invariants, per **boundary-discipline**. Retain operation-specific runtime checks when types or earlier validation do not establish the required condition. Keep core rules pure and effectful wiring at its owning boundary.
- Security and throughput. Apply [Security by Construction](../../principle-security-by-construction/SKILL.md) and [Design for Throughput](../../principle-design-for-throughput/SKILL.md). Make relevant authority/data isolation and whole-flow cost decisions visible in the sketch, including resource ownership and safe defaults. State assumptions and evidence gaps; do not turn the design target into a claimed benchmark result.
- Single source of truth per invariant. Derive instead of sync.
- Idempotent state transitions where applicable, per the **make-operations-idempotent** principle skill. Ask what happens if the operation runs twice or crashes halfway.
- Reader load. Remove indirection that adds no useful contract, per **minimal-change** and **minimize-reader-load**. Evaluate framework facades, service contracts and class adapters by the decisions they hide; file count or direct delegation alone does not establish that a boundary is redundant.

You are one of the independent candidate runners using the configured runtime roles. Produce the best design your assigned perspective can make. Don't hedge against the others. Differences between candidates are the signal used to pick a base and graft. Converging on a safe-looking middle defeats the exploration.
