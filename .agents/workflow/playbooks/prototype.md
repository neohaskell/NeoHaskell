### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

Explore alternatives quickly to pick the right design cheaply. Keep the implementation throwaway and scope it to the decision. Formal tests must establish the relevant contracts; production polish is not the goal. Propose variations the user didn't ask for, throw an approach away and try another.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to Feature.
2. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, let the user pick directions before building. Skip when the direction is set.
3. Build throwaway in an isolated directory under repository-root `.agents-state/prototypes/<decision>/`, separate from production source; keep captures and experiment notes there too. For a visual decision, use vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, and a dev server with hot reload; no production framework is needed. For a framework API, type, or generator decision, use a minimal Haskell consumer and the actual NeoHaskell/GHC components needed to answer it. For a behavioral or timing decision, use the smallest runner that executes the relevant behavior. Keep the implementation small and avoid reusable abstractions. Include formal tests for the relevant contracts of the variants.
4. When comparing alternatives, use one selector appropriate to the experiment: buttons or a keypress for visual variants, or labeled fixtures/runner options for framework and compiler variants. This is the **exhaust-the-design-space** principle skill made cheap.
5. Verify each variant with formal tests at the matching boundary. Use focused Hspec examples and meaningful QuickCheck properties for Haskell behavior, compiler consumer fixtures for type/generated-interface claims, and browser assertions for relevant UI interactions or layout constraints. Derive expected outcomes from the contract, not from the variant under test; avoid tautological tests. Demand the required pure results and execute Task/decision effects when checking behavior. For a visual decision, also screenshot each variant and drive the interaction. Screenshots, logs, printed output, and timings support the formal checks. When timing determines the choice, validate each variant's correctness and follow `benchmark-checklist` for the measurements. Record the test commands and results.
6. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction to **Feature** (or `architect` for the shape) for the real build.

**Reply:** the variants explored, the formal test commands and results, the evidence (screenshots for a visual decision, the observed output or timing for a behavioral one), tradeoffs, your recommendation, and the scratch path. Say plainly that the prototype is throwaway.
