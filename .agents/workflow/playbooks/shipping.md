### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

Shipping begins when landing is in scope under the [task completion policy](../../skills/orchestrate/references/task-completion.md). A standalone request to review or reach merge-ready stays within `babysit.md`. Keep verdicts, tested head/base snapshots, commands, logs and stack boundaries under repository-root `.agents-state/shipping/<run>/`.

1. **Use GitHub CLI and verify each PR independently before it lands.** Follow `AGENTS.md` for available verifier roles and execution facilities. Each PR needs a verifier who did not write its code; batch verification to available capacity without dropping PRs. The verifier compares parent against head at the relevant boundary and records `PASS`, `PASS+NOTES`, or `FAIL`, with tested head/base SHAs, commands, expectations, results and limitations. Publish the verdict on the PR as part of the authorized shipping workflow, with sensitive evidence kept local. When independent verification is unavailable, report the gap rather than counting the author's checks as independent.

   For internal NeoHaskell changes, verify the actual library, compiler or framework contract: representative consumer compilation for public API and Template Haskell generation; demanded pure results and executed Tasks/decisions for runtime claims; command execution, event storage, query/projection visibility or other affected service interactions when relevant. Use meaningful behavioral/property checks with independent expectations. Use the matching `control-ui` or `control-cli` skill for those surfaces, and `benchmark-checklist` when performance or consumer compilation cost is part of the claim. CI evidence can support the verdict when it tests the relevant behavior, but green status and a review approval alone are not the independent verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. Notes must describe non-blocking limitations, not failed acceptance criteria. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code and its inputs.** Record the verified parent/head snapshots and relevant compiler, dependency, build-flag, generator, fixture and runtime inputs. A matching patch ID is a useful comparison aid, not proof that the tested behavior survived a rebase. Whitespace-sensitive source and changed dependencies can invalidate that inference. Matching build output also does not establish that new tests ran or that runtime configuration is equivalent.

   After a changed head/base or relevant input, rerun the affected compiler, behavior and integration checks against the current candidate. An independent verifier may carry forward unaffected evidence only with a concrete explanation of unchanged inputs and coverage. Tests, documentation and configuration changes still need their own relevant checks and review; filenames alone do not make them harmless. If equivalence cannot be established, obtain a fresh verdict. Keep current-head required checks and branch rules satisfied separately from this verification judgment.
4. **Land bottom-up, one PR at a time.** Discover the actual trunk/default branch. Before each merge, use `babysit.md` to re-check current head/base, checks, reviews, threads and branch rules. Confirm this PR targets trunk, not its parent's branch. Squash merge with a Conventional Commit subject that describes the final diff. Prepare the subject and body under [Opening a PR](opening-a-pr.md) and pass both explicitly so intermediate commit messages do not become the squash message. Submit the verified head with `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head> --subject '<type>(<scope>): <summary>' --body-file <reviewed-body-file>`, respecting queue rules. If squash merging is unavailable, report the policy conflict instead of choosing another merge strategy. Do not bypass requirements. Read back `state`, `mergedAt`, `mergeCommit`, `headRefOid` and `baseRefName`; queueing or enabling auto-merge is not a completed merge.

   Before a parent's squash merge, record the exact old parent boundary used by the next child. Once GitHub confirms the parent merged into trunk, have the exclusive topology owner reconcile the child with that actual trunk and retarget it with `gh pr edit <pr> --repo <owner/repo> --base <trunk>`. Use authorized normal integration when it preserves the child-only diff. If history rewriting is necessary, obtain the required authorization and replay only the child's own commits after the recorded boundary, publishing with an explicit expected-head lease. Inspect the resulting diff so merged parent changes are not replayed or lost. A base edit alone does not move commits. Update the stack map and PR links. Preserve other writers' work. Apply step 3 to the resulting candidate, then wait for its current checks and valid verdict before merging it.
5. **Leave the stack alone while it lands.** Step 4's owner-controlled move of the next PR is the only planned branch/base change. Use one supervisor with the direct GitHub status and host waiting facilities from `babysit.md`, continuing until the ceiling actually reads merged. Do not use a CI watcher as proof of merge completion. A base that moves to trunk when its parent merges is expected, not damage to repair.

   If a queue is required, or explicitly authorized auto-merge is used, keep the pending PR's head/base frozen under the owning workflow. Do not arm deferred merging when that ownership control cannot be maintained. The head-match option is a submission check; do not rely on it to preserve the validity of a verdict after later pushes. If a head/base changes, suspend further landing, withdraw pending automation where permitted, and re-establish current evidence before resuming. If a merge stalls, find out why before changing anything. Report monitoring limitations when the host cannot persist beyond the active session.
6. **Stop at the evidence ceiling.** Extending the verified run takes new verdicts and a new pass through step 1. If the task still has authorized work, obtain those verdicts and continue without a new human review request.

**Reply:** the verified run and its ceiling, each PR's verdict and verifier with tested head/base, what landed and how it was confirmed, what remains queued or pending, and what the next gap needs.
