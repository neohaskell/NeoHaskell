### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and implementation through the available roles and execution facilities in `AGENTS.md`, stay in the lead, and give each worker a specific scope. Respect available capacity and report unavailable delegation rather than inventing workers or configuration. Keep reproduction inputs, diagnostics, logs and before/after evidence under repository-root `.agents-state/bug-fix/<run>/`.

Be scientific. Every fix traces to an observed failure and a verified cause. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

Framework export, TH marker and generated-API fixes also follow
[NeoHaskell consumer verification](../../skills/neohaskell-consumer-verification/SKILL.md)
for the same-PR starter and testbed migration contract.

1. Reproduce it yourself at the affected boundary. For a compiler, public type/API or Template Haskell failure, use a minimal representative consumer and capture the actual compiler/splice result under the relevant flags and dependencies. For pure behavior, demand the result; for Tasks or decisions, execute them; for service interactions, observe the actual affected command, storage, query or downstream result rather than stopping at task construction or command acceptance. Use the matching control skill for CLI/UI failures. Ask the user to reproduce only with a stated, specific reason the available surface cannot reach the target, after driving it as far as it goes. If it will not reproduce directly, synthesize the trigger, tighten conditions or instrument the relevant boundary. Report an unconfirmed reproduction honestly rather than shipping a guessed fix.
2. Binary-search the cause. Form candidate hypotheses, then rule them out until one survives. Seed them with `how` over the affected subsystem and `why` for regression history. Each pass, take the split that cuts the most remaining problem space, get evidence and eliminate. Trace changed types, instances, exports, generators, build inputs and their consumers as well as the failing file. Use compiler diagnostics or controlled compilation for compile-time claims, demanded values for pure claims, and executed effects/observed outcomes for runtime claims. When state is unclear, add focused diagnostics and read the actual results. Drive a long or stubborn hunt with supported execution/wait facilities from `AGENTS.md`. Confirm the surviving mechanism at its relevant boundary before designing the fix. A green build proves only the compiler contracts it actually checks.
3. Plan the fix. Use `architect` when the fix needs a non-trivial design decision about public contracts, representation, module/service ownership, generation strategy or effect/concurrency boundaries. Merely crossing between existing pure helpers does not require a new architecture exercise. Delegate implementation through the configured roles in `AGENTS.md` with a specific scope. Follow [NeoHaskell best practices](../../skills/neohaskell-best-practices/SKILL.md) and [code guidelines](../../skills/neohaskell-code-guidelines/SKILL.md). When concurrency is implicated, locate the owning subsystem and choose the appropriate existing NeoHaskell primitive rather than adding coordination across pure callers.
4. Verify at the same boundary. The original repro now passes for the intended reason. "Inconclusive" or wrong-surface is not a pass. Flag it. Use independently specified expectations: a meaningful unit/property check can establish the covered pure behavior; compiler consumer checks can establish the covered type/generation contract. Neither establishes unobserved service or runtime behavior. For those claims, execute the affected flow through its observable completion and check nearby contracts. Avoid tautological tests and do not weaken assertions to match a wrong implementation.
5. Stage the commits so the failing regression proof comes before the fix in git history. Follow `tdd` when there is a practical focused regression test path, using Hspec, meaningful QuickCheck properties or compiler/consumer fixtures as appropriate. An integration-heavy bug is not by itself a reason to omit proof. If adding a new durable test is impractical under `tdd`'s fallback, use the closest useful executable regression check and explain the limitation. Follow **sequence-verifiable-units**: keep the types, instances, generators and consumers required for one contract change in a coherent unit, preserving the failing-before/passing-after evidence.
6. Run **Opening a PR**.

**Reply:** what was broken, root cause, fix, how you verified. Include the failing-then-passing compiler or runtime repro commands and relevant output, along with any verification limits. Redact sensitive values.
