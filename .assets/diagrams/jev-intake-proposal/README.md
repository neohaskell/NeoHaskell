# Proposed Jev-driven intake

Review draft only. This does not change the running intake process, task registry,
evaluator, or pipeline policy. Generated by `build.py`; the editable source is
`jev-intake-proposal.drawio`. The three PNG pages were structurally validated and
visually reviewed. `review.html` is a standalone, offline review copy.

## Recommendation

Make intake a small program that produces a structured task record. Code reads
facts and controls execution. Jev supplies bounded semantic judgments. An LLM
receives only a verified task and the part that still requires generation or
reasoning. Minimize total inference and wrong automatic decisions, rather than
maximizing the number of Jev questions.

Keep all 22 requested task names as user-facing presets, but normalize them into
three independent fields. Bug fix describes work; autonomous run describes how to
run it; opening a PR describes a lifecycle action. They can all apply to one
request. Issue versus ad hoc is separate source metadata. Existing bug/feature
classification can remain part of work type rather than owning the whole flow.

The taxonomy diagram preserves every requested name. Its definitions are proposed:

- Work: authoring a skill, bug fix, eval, feature, hillclimb, investigation,
  multi phase plan, perf issue, prototype, refactoring, runtime forensics,
  trace forensics.
- Mode: autonomous run, autopilot full, autopilot stack, babysit, orchestrate.
- Lifecycle actions: opening a pr, pause safely, session pickup, shipping,
  worktree cleanup.

Perf issue, runtime forensics and trace forensics can share an investigation
engine with different evidence sources. Hillclimb composes an experiment loop
with evaluation. Babysit composes observation with a catalog of known recovery
steps. Autopilot full composes the selected work's stages; autopilot stack adds
explicit dependency ordering. Unknown and mixed requests remain expressible.
Multiple work items use an explicit task list or a known sequence template;
novel dependency planning is a bounded LLM task.

## Proposed flow

1. Read explicit settings and exact facts: branch/worktree, current run state,
   request IDs, checkpoints and available budgets. Preserve user constraints.
   A recognized pause command takes precedence; a pickup validates a checkpoint
   and reuses its plan unless the user requests changes.
2. If required intent fields are missing, batch independent Jev questions:
   Choice for primary work and mode; individual Nouls for additional actions
   and secondary intents. Explicit structured settings bypass inference. Every
   Choice offers unknown/no-match where appropriate. A selected mode never
   silently expands the user's granted scope.
3. A versioned playbook declares required inputs, permitted tools, evidence
   sources, output schema, stop conditions and optional generation steps. Code
   retrieves its candidates from maintained registries. Full catalog coverage
   or candidate-recall checks matter: Jev cannot select an omitted candidate.
4. Batch only the remaining semantic questions over the retrieved evidence.
   Use one Noul per independently applicable capability, a common evidence-fit
   Score rubric to rank candidates, and Choice for bounded next actions. Several
   capabilities may legitimately apply. Dependent questions wait for the evidence
   their earlier answers identify; they cannot consume answers within one batch.
5. Code validates IDs, evidence freshness and required fields, applies explicit
   uncertainty rules only to relevant questions, and compiles an intake record.
   An uncertain answer on an unused speculative branch does not block progress.
   Scores and model confidence are different quantities, neither is a permission.
6. Classify an unresolved gap using missing-field facts and Jev's typed signals.
   Fetch observable evidence within a retry budget; ask a specific question when
   user intent is missing; call an LLM for a novel interpretation or plan. On
   budget exhaustion, stop with the named gap rather than guessing. Revalidate
   any returned proposal. Avoid circular retries with unchanged state.
7. Dispatch the record to a registered playbook. Pause, status, pickup, known
   evaluation runs and some maintenance operations can often use code alone.
   Feature implementation and skill authoring still need code/prose generation;
   eliminating their intake LLM does not eliminate the implementation LLM.

Cache raw judgments under the request, evidence, question/rubric, model and
policy-relevant context versions. Changes invalidate affected judgments. Reading
mutable workspace facts remains necessary; an old cached judgment is not proof
that the worktree is still in the same state. Changing only a display weight may
reuse scores without another model call.

## Example intake record

```json
{
  "work": "bug_fix",
  "secondary_work": [],
  "mode": "autonomous_run",
  "actions": ["session_pickup", "opening_a_pr"],
  "constraints": {
    "branch": "subtle-deer",
    "preserve_worktree": true
  },
  "targets": ["verified registry IDs filled after localization"],
  "stop": "the user-agreed boundary",
  "evidence": ["source references and hashes"],
  "unresolved": []
}
```

This is a shape illustration, not a classified request or permission to open a
PR. Free-form constraints need exact source spans or an explicit user setting;
Jev can select spans but should not invent new constraints or path names.

## Three concrete primitive questions

- Choice: “Which registered work type describes the requested outcome?” Include
  the work presets, mixed, action-only and unknown. Treat execution mode as a
  separate question, not a competing work type.
- Noul: “Does capability C own any part of this requested change, according to
  its responsibility and this request?” One question per candidate supports
  multi-owner changes. Another independent Noul can detect a request to open a PR.
- Score: “How directly does this source support candidate C?” Proposed levels:
  0 unrelated/contradicted; 1 incidental overlap; 2 partial, with a missing fact;
  3 direct support. Keep the probability distribution and confidence separately.

Do not hardcode the previous experiment's thresholds into this new task family.
Each question needs examples and its own consequences considered. The earlier
three prompt rewrites did not improve raw judging accuracy; the architecture is
an experiment to test, not a demonstrated performance gain.

## Suggested first iteration

First introduce the task record and 22 preset definitions. Create labeled requests
that combine work, mode and actions, plus ambiguous and unknown cases. Compare
Jev classification with the current intake without letting it execute anything.
Then move localization decisions one at a time. Finally add controller playbooks
for pause/pickup, evaluation, babysit and other repeatable operations.

Track wrong automatic decisions together with automatic coverage; unnecessary
clarification; evidence validity; preservation of constraints; intake LLM-free
rate; model calls/tokens; latency and repeat stability. Measure the complete
workflow as well as isolated questions. Keep tuning cases separate from later
validation, and use exact reference checks where available. A faster result with
more wrong routes is not an improvement.
